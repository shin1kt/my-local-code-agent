# 評価の内容: 何を作らせ、どう採点しているか

小さな Python プログラムの修正や実装を5課題用意し、モデルごとに各課題を既定で3回ずつ解かせます。
成果物を**モデルに渡していないテスト**で自動採点し、合格数を数えます。

実行方法は [setup-linux.md](setup-linux.md) を参照してください。

> このページには各課題の答えにつながる内容が含まれます。評価するモデルには読ませないでください。

## 課題

| 課題 | 最初に渡すもの | 依頼 | 見たい力 |
|---|---|---|---|
| `bugfix` | バグ入りの `stats.py` と失敗するテスト | テストが通るように直す | テスト実行、修正、再確認の基本動作 |
| `feature` | 文字列処理の `text_utils.py` | `slugify` 関数を追加する | 文章で書かれた条件を正確に実装する |
| `rename` | 4ファイルの `app/` | `get_user` を `find_user_by_id` に変える | 複数ファイルを漏れなく、余計な箇所に触れずに直す |
| `cross_file_bug` | 3段に呼び出しが連なる `shop/` とテスト | 合計金額が合わない原因を直す | 呼び出し元をたどって原因を見つける |
| `from_spec` | 仕様書 `SPEC.md` だけ | LRUキャッシュを新規に作る | 仕様を読み、ゼロから書く |

間違えやすい点:

- **`bugfix`**: 空リストの平均は 0、要素が偶数個なら中央値は中央2つの平均、という2つのバグがある。仕様は docstring とテストに書いてある。
- **`feature`**: `"日本語"` のように結果が空になる入力では `ValueError`。`"café au lait"` は `caf-au-lait` になる。
- **`rename`**: 名前の似た `get_user_names` があり、単純な一括置換では壊れる。
- **`cross_file_bug`**: 症状は `order.py` に出るが、原因は2つ先の `rules.py` にある。`>` と `>=` の誤りと、最高ではなく最初に一致した割引率を返す誤りの2つ。
- **`from_spec`**: `get` した項目も「最近使った」扱いになる。値が `None` の場合も区別する。

### ファイルの場所

```
evals/tasks/<課題名>/
├── task.json    依頼文(prompt)、変更禁止のファイル(protected)、採点に使うテスト(checks)
├── workspace/   モデルに渡すファイル
└── hidden/      モデルに渡さない非公開テスト
```

## 評価の流れ

1. `workspace/` を一時ディレクトリにコピーする
2. エージェントに依頼文を渡す(既定で最大25ステップ・10分)。モデルはファイルを読み、編集し、コマンドを実行して結果を見ながら直す
3. `protected` のファイルが変更・削除されていれば、その時点で不合格にする
4. 成果物を別のディレクトリにコピーし、`hidden/` のテストを加える
5. `checks` のテストをすべて実行し、全部通れば合格、1つでも失敗すれば不合格にする

採点は成果物だけを見ます。モデルの「完了しました」という報告は合否に関係なく、時間切れやステップ上限で終わっても、その時点の成果物が正しければ合格です(`results.json` の `status` で区別できます)。

### 採点の例(`cross_file_bug`)

モデルに見えるテストが確認するのは、数量が 9・10・120 の場合だけです。非公開テストは、割引が切り替わる境界をすべて確認します。

```python
expected = {0: 0, 9: 0, 10: 5, 49: 5, 50: 10, 99: 10, 100: 20, 500: 20}
self.assertEqual({q: discount_rate(q) for q in expected}, expected)
```

見えているテストの値だけに合わせた修正は不合格になります。

## 不正への対策

- **テストや仕様書の書き換え**: `protected` に指定したファイルを変更すると不合格。実際に、テストを書き換えて通したモデルがあったため。
- **非公開テストの参照**: 作業ディレクトリには置かない。ファイル操作は作業ディレクトリ内に限り、コマンドは許可リストで制限する。
- **課題自体の検証**: どの課題も「未着手なら不合格、正解なら合格」になることを `tests/test_evals.py` で確認している。

`tests/` は**エージェントと採点の仕組みを検査するもの**で、LLM は使いません。モデルの性能評価とは別物です。

## この評価の限界

- **課題が小さい**: 数ファイル規模なので、上位モデルでは満点が並んで差がつかない可能性がある。大規模なコードでの実力はわからない。
- **回数が少ない**: 3回では偶然の影響が残る。僅差は優劣とみなさない。
- **見ているのは動作だけ**: 読みやすさや、変更が最小限かどうかは採点しない。必要なら `results/` の `.diff` を見る。
- **完全な隔離ではない**: モデルが書いた Python は実行時に通常のユーザー権限で動くため、作業ディレクトリの外も読める。
- **非公開テストもこのリポジトリで公開されている**: 評価中のモデルには渡さないが、将来のモデルが学習する可能性はある。
- **対象が狭い**: Python だけで、依頼文も日本語だけ。

## 課題を追加する

1. `evals/tasks/<課題名>/` に `task.json`、`workspace/`、`hidden/` を作る
2. `tests/test_evals.py` の `SOLUTIONS` に正解例を足す
3. `python3 -m unittest tests.test_evals` で、未着手なら不合格、正解なら合格になることを確かめる
